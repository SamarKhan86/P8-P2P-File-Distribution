# `src/sha256.c` — SHA-256 implementation

## Purpose in one sentence

`sha256.c` implements the SHA-256 cryptographic hash function used to calculate and verify piece digests without requiring an external crypto library.

## Why this file exists

A receiver needs to check whether a piece's bytes match the expected content before marking it verified or sharing it as a verified piece. The expected hashes are stored in metadata, and this module calculates the hash of actual byte buffers. A self-contained implementation also keeps the build dependencies small.

## Where it fits

Declarations and `SHA256_CTX` are in [`include/sha256.h`](../../include/sha256.h). `metainfo.c` hashes pieces while creating a manifest. `piece_manager.c` hashes existing pieces during resume scanning. `peer_transfer.c` hashes newly received piece bytes before writing them as verified.

## Important data

`SHA256_CTX` stores:

- a 64-byte partial input block;
- the number of bytes currently buffered;
- the total processed bit length;
- eight 32-bit working state words.

SHA-256 operates on 512-bit (64-byte) blocks and produces a 256-bit (32-byte) digest.

## Functions

### `static void transform(SHA256_CTX *ctx, const uint8_t data[])`

Private compression routine for one 64-byte block. It expands the input into the message schedule and performs the 64 SHA-256 rounds using fixed round constants and bitwise operations, then adds the result back into the eight state words. It is static because callers should use the public streaming API, not call block compression directly.

### `void sha256_init(SHA256_CTX *ctx)`

Initializes the context's buffered length and bit count to zero and sets the eight state words to the standard SHA-256 initial values. A null context is ignored.

### `void sha256_update(SHA256_CTX *ctx, const uint8_t data[], size_t len)`

Adds data to the running digest. It accepts arbitrary chunk lengths, fills the 64-byte buffer, and calls `transform()` whenever one complete block is ready. It updates the processed bit count per full block. Null context and null data with a non-zero length are ignored.

### `void sha256_final(SHA256_CTX *ctx, uint8_t hash[])`

Applies SHA-256 padding, appends the original message bit length in big-endian form, processes the final block or blocks, and writes the eight state words as 32 output bytes. Null context or output is ignored.

### `void sha256_buffer(const uint8_t data[], size_t len, uint8_t hash[])`

Convenience wrapper for one complete buffer: initializes a temporary context, calls `sha256_update()`, and finalizes the digest. This is the function most other project modules use. It accepts an empty buffer with length zero; callers should supply a valid output pointer.

## How verification works in this project

1. The metadata generator computes a SHA-256 digest for each piece.
2. A receiving peer gets raw bytes in a `MSG_PIECE` message.
3. `peer_transfer.c` calls `sha256_buffer()` on those bytes.
4. It compares all 32 digest bytes with `meta.piece_hashes[piece_idx]`.
5. Only when the digest matches and the file write succeeds is the piece marked `PIECE_VERIFIED` and advertised via `HAVE`.

## Important distinction

A cryptographic hash provides a content-integrity check against the expected digest. It does not encrypt the file, authenticate the identity of a sender, or by itself establish that the metadata is trustworthy. In this project the expected hash comes from the `.meta` manifest distributed to peers.

## Limitations

This is hand-written cryptographic code, so it needs careful testing before use in security-critical production systems. Its current purpose is educational and to avoid an external dependency. No separate test vectors were present in the inspected `tests/` directory; the integration test exercises hashing through metadata generation and piece verification, but that is not a complete independent validation of every SHA-256 edge case.

## Likely viva questions

**Q: Why is SHA-256 useful for pieces?**

A: A piece can be corrupted during storage or transfer; comparing its digest against metadata detects a mismatch with very high probability.

**Q: Is SHA-256 encryption?**

A: No. It is a one-way hash function and does not hide the original bytes.

**Q: Why does a piece hash have 32 bytes?**

A: SHA-256 outputs 256 bits, and 256 divided by 8 is 32 bytes.
